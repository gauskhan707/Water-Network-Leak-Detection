Project introduction

Why this case study exists

This project asks a deliberately narrow question: can hourly anomaly scores classify observations associated with recorded leak events? The answer must be read as a dataset-based learning result, not as a deployment claim.

Scope guardrail
fault_d7 is a proximity label covering approximately ±7 days around recorded events. It is not a live leak indicator and does not measure detection lead time.

The data combines SCADA, energy, environmental, and groundwater anomaly scores with a binary event-proximity label.

03 / 26

Data quality

What had to be checked before modeling

The dataset has no duplicate rows or duplicate timestamps, but it has 16,804 missing cells across 5,707 rows. Scores stay within the documented 0–100 range and many are exactly zero by design.

Critical data-quality finding: the timestamp strings use a mixed convention. Applying the documented format blindly produces 22 backward clock jumps and 68 apparent label changes; the inferred month/day rule restores a strict hourly sequence and 16 label changes.
04 / 26

Exploratory data analysis

What patterns are visible before modeling

Class balance changes sharply by month, most anomaly scores are zero with occasional spikes, and no single score separates the classes strongly. These patterns justify time-aware validation and a skeptical interpretation of row-level metrics.

05 / 26

Target and class balance

What <code>fault_d7</code> means

fault_d7 = 1 marks an hour within approximately seven days before or after a recorded leak event. Class 1 is the positive class and the majority: 6,432 rows (73.6%) versus 2,305 rows (26.4%) for class 0.

Why this matters: a classifier that always predicts 1 already achieves 73.6% overall accuracy and 89.0% accuracy on the final test. Accuracy, recall, and F1 must therefore be read beside the baseline.
06 / 26

Date and time understanding

Why time is part of the problem

The correctly reconstructed data contains 8,736 one-hour steps after the initial 31 December 2021 observation. Labels form only 17 contiguous blocks, not thousands of independent events. The label never changes inside a calendar day.

07 / 26

Feature preparation

What the models are allowed to see

The model uses 18 anomaly scores plus hour and day_of_week, for 20 numeric features. It excludes the raw timestamp, target, year, month, and day. Missing-value indicators are added during preprocessing rather than hand-built into the feature set.

08 / 26

Leakage analysis

How false confidence can appear

Random splits allow neighboring hours and future conditions to appear in both training and validation. In the teaching demonstration, the same type of model reaches ROC-AUC 1.0 with a random split but only 0.6079 chronologically.

Wrong approach / teaching demonstration: the random split is shown only to expose leakage and is never used for the final evaluation.

The valid workflow fits transformations on earlier data only, uses current-row features, and keeps the final period untouched.

09 / 26

Chronological train / validation / test split

Past → development → untouched future

The first 60% of the ordered timeline is training, the next 20% is validation, and the final 20% is the untouched test. The class mix changes from 62.0% in training to 93.1% in validation and 89.0% in test, while groundwater sensors are missing in 82.4% of the test period.

10 / 26

Preprocessing

Fit transformations only on the past

Median imputation and missingness indicators produce 34 columns from the 20 original numeric features. Logistic Regression additionally uses standardisation. Random Forest and HistGradientBoosting use imputed, unscaled values. All learned preprocessing parameters come from training folds only.

11 / 26

Baseline

The reference every ML model must beat

The baseline predicts the most common training class, which is 1. On validation it reaches 0.931 accuracy and 0.964 F1 without reading a sensor. On the final test it reaches 0.890 accuracy, 1.000 recall, and 0.942 F1. Its specificity is 0, which is why the baseline must not be judged by a single metric.

12 / 26

Classification models

A compact, sensible model set

The project keeps Logistic Regression, Random Forest, and HistGradientBoosting. They represent a transparent linear model, a bagged tree ensemble, and a sequential boosting model. Each is trained and evaluated without changing the time-aware methodology.

13 / 26

Classification metrics

Read the model from multiple angles

Accuracy, precision, recall, F1, ROC-AUC, and PR-AUC are all retained. Confusion-matrix counts make the operational meaning explicit: a false positive is a false alarm, while a false negative is a leak-proximity observation the classifier misses.

Why accuracy can be misleading

Majority-class behavior can flatter a model

Because class 1 is the majority, a do-nothing predictor can have high accuracy, recall, and F1. The project therefore compares every model with the baseline, uses ROC-AUC as the primary model-selection metric, and reports specificity and balanced accuracy.

15 / 26

Time-series cross-validation

Validation that respects the calendar

TimeSeriesSplit is applied only to the development period with a 336-hour (14-day) gap. The baseline beats every ML model on all six tracked metrics. Mean ROC-AUC is 0.500 for the baseline versus 0.385 for Logistic Regression, 0.279 for Random Forest, and 0.309 for HistGradientBoosting.

16 / 26

Hyperparameter tuning

A small, reproducible GridSearchCV

GridSearchCV tests eight Logistic Regression combinations of regularisation strength and class weighting using the same time-series splits. The best mean ROC-AUC is 0.406 with C=0.01 and class_weight="balanced"—an improvement over 0.385, but still below chance and below the baseline.

17 / 26

Model comparison

Selection rule and development result

The tuned Logistic Regression is the best ML model by the pre-declared ROC-AUC rule, but no ML model beats the do-nothing baseline. This distinction is preserved: the tuned model is evaluated to understand its behavior, while the baseline remains the stronger decision rule on this dataset.

18 / 26

Final model and untouched test

The one-time future evaluation

The final test contains 1,748 hours and 89.0% class 1. It is evaluated only after model development and selection. The tuned Logistic Regression scores 0.292 accuracy, 0.270 recall, 0.310 ROC-AUC, and 0.823 PR-AUC, all worse than the baseline except precision.

What the final errors mean

The final model produces 90 true negatives, 102 false positives, 1,136 false negatives, and 420 true positives. In this context, the 1,136 false negatives mean the model misses most observations inside the defined leak-proximity window.

ROC and Precision–Recall curves

Threshold-free performance views

The ROC curve stays below the diagonal and the ROC-AUC is 0.310. PR-AUC is 0.823, which must be compared with the final-test class-1 prevalence of 0.890. Neither curve supports the claim that threshold adjustment would rescue the learned ranking.

21 / 26

Error analysis

Where the model fails in time

Errors are structured, not random. The model produces 96 false positives during 28–31 October when the groundwater score is high, then 1,136 false negatives during the long groundwater outage from November into December. The analysis reports these patterns without inventing physical causes.

22 / 26

Feature importance and interpretation

What the model relies on

Permutation importance and Logistic Regression coefficients show that groundwater features receive large weights, but their relationship with the label changes over time: groundwater-level correlation moves from +0.36 in training to −0.84 in the final test where it is observed. Importance is predictive reliance, not causation.

23 / 26

Model reality check

Look past the headline metric

On the final test, the baseline has balanced accuracy 0.500 while the tuned model has 0.369. The tuned model has precision 0.805 but misses 73% of class-1 hours, has ROC-AUC below chance, and is affected by long sensor outages. These are the results that matter more than a flattering single score.

Bottom line: the final model is not production-ready and should not be described as a leak detector.
24 / 26

Risk analysis

Practical implications

Key risks include false alarms, missed in-window observations, class imbalance, temporal dependence, the symmetric label definition, sensor outages, drift, uncertain timestamp reconstruction, and limited coverage of one anonymised network over one year. Operational use would require independent periods, event-level evaluation, alert-cost analysis, and a genuinely forward-looking target.

25 / 26

Limitations

What this project cannot prove

  • It does not prove real-time leak detection or early warning.
  • It does not generalise to other networks, years, sensors, or climates.
  • The published anomaly scores cannot be audited here for their own upstream leakage.
  • Row-level metrics overstate certainty because neighboring hours are dependent and only about eight leak periods are present.
  • The timestamp repair rule is an inference that should be confirmed by the dataset authors.
26 / 26

Conclusion

What the evidence supports

The corrected time order reveals a clean hourly sequence but also exposes strong temporal structure, uneven sensor availability, and a majority-class target. Time-aware validation shows that the anomaly scores used in this setup do not reliably classify later observations. The strongest portfolio lesson is methodological: preserve time order, audit leakage, compare with a baseline, keep the final test untouched, and report weak results honestly.

Final conclusion: this is a complete, honest leak-proximity classification study—not a guaranteed real-time leak detection system.
